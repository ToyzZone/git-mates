## Summary

- **HEAD sits on `refs/heads/gitbutler/workspace`, a merge commit of every applied branch tip.** The index is set to that commit's tree, so `git status` and `git diff` show only uncommitted work. A `pre-commit` hook blocks `git commit` there. A commit made anyway (`--no-verify`) makes every `but` command refuse until `but teardown` or a `git reset --soft`. **[12]**
- **GitButler is moving away from the workspace commit.** Since 2026-10-13 "single-branch mode" is always on. HEAD may sit on a normal branch, and `but` only builds a workspace commit when a second branch is applied. The hooks are now called "legacy" (`but teardown --remove-hooks`). The docs say it is "working toward a plain Git mode that switches into a workspace only when multiple concurrent branches are needed". **[12] [why]**
- **Adjacent lines: the lock check and the commit check disagree.** The lock (dependency) check is strict line overlap with 0 context lines, plus a 1-line margin only for reorders and deletion points. Committing cherry-picks with a 3-way merge that, "like Git", conflicts on touching changes. So a hunk next to another branch's lines is usually not shown as locked, but committing it to its own branch is rejected for the whole file. GitButler never puts another branch's lines into a commit: it rejects instead. **[13]**
- **Nothing enforces locks or ownership any more.** In March 2026 GitButler stopped forcing locked hunks onto their branch. In August 2026 the CLI stopped assigning hunks at all. Stacking is never automatic. The docs say "The branch routing is the agent's job". **[13] [why]**
- **Parallel branches that conflict cannot both be applied.** The workspace merge drops a conflicting branch, and applying a conflicting branch aborts by default. **[13]**
- **Base moves (`but pull`): every lane bottom is rebased onto the new target.** Commits already upstream are dropped. Conflicts never stop the rebase: they become "conflicted commits" with extra directories in their tree. Uncommitted work is 3-way merged and may get conflict markers. Branches found integrated upstream are deleted locally. **[12] [14]**
- **Throwing a branch away:** `but branch delete` drops the branch's commits and ref, after an oplog snapshot. Unapply keeps the branch and removes its files from disk. Unapply commits only *assigned* WIP as a "WIP Assignments" commit, and the CLI no longer assigns. So a session's uncommitted changes have no owner to follow. **[14]**
- **Undo is repository-wide.** A snapshot holds the whole working directory (untracked files included, no size limit), the index, metadata and copies of the applied branches' commits. Restoring it checks out that whole tree, so every session's WIP goes back to that moment. Branches that were already unapplied at snapshot time are not in it. **[14] [why]**
- **Agents today: instructions, not hooks.** The 2026-05-19 removal named no replacement. Since 2026-06-24 `but agent setup` installs a skill and writes a "Version control" block into `CLAUDE.md`/`AGENTS.md`: "Use a dedicated GitButler branch for each agent session" and "Commit only changes that belong to that session". The skill says "Never run `git add`, `git commit` ...". Nothing enforces either rule. **[why]**
- **License:** FSL-1.1-MIT licenses GitButler's *code*. It bars only a "Competing Use" of that code, and its terms follow every copy and derivative. It says nothing about ideas. Each version becomes MIT two years after it is published. Whether GitButler holds patents is **(unverified)**. **[why]**

## 1. The workspace **[12]**

### HEAD, refs and where state lives

- **HEAD points at `refs/heads/gitbutler/workspace`** ([but-core/lib.rs#L128](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/lib.rs#L128)). The old name `gitbutler/integration` is still accepted ([operating-modes/lib.rs#L13-L21](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-operating-modes/src/lib.rs#L13-L21)). Edit mode uses `refs/heads/gitbutler/edit`.
- **Three modes**, derived from HEAD alone: `OpenWorkspace` ("on the gitbutler/workspace branch"), `OutsideWorkspace` ("the user has chosen to leave the gitbutler/workspace branch") and `Edit` ([operating-modes/lib.rs#L105-L154](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-operating-modes/src/lib.rs#L105-L154)).
- **The graph classifies the workspace three ways** ([projection/workspace/mod.rs#L76-L104](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-graph/src/projection/workspace/mod.rs#L76-L104)):
  - `Managed`: HEAD on the workspace ref, which points at a workspace commit.
  - `ManagedMissingWorkspaceCommit`: the workspace ref "was *possibly* advanced by hand and does not point to a managed workspace commit (anymore)".
  - `AdHoc`: "A segment is checked out directly", that is, a normal branch (single-branch mode).
- **Session branches are plain local branches.** New branch names are `refs/heads/<name>`, by default derived from the author's initials ([branch/generate.rs#L10-L18](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/branch/generate.rs#L10-L18)). The docs' example still shows the older `refs/gitbutler/<name>` ([workspace-branch.mdx#L27-L30](https://github.com/gitbutlerapp/gitbutler-docs/blob/fde5f9265e7f8aa37377919c851cc744a97f1e8a/content/docs/workspace-branch.mdx#L27-L30)).
- **Metadata lives in `.git/gitbutler/`** ([storage_path.rs#L21-L39](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-project-handle/src/storage_path.rs#L21-L39), [#L112](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-project-handle/src/storage_path.rs#L112)): `virtual_branches.toml` plus a `but.sqlite` database ([but-ctx/lib.rs#L845-L863](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-ctx/src/lib.rs#L845-L863), [but-db/handle.rs#L9](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-db/src/handle.rs#L9)).
- **Entering the workspace sets `log.excludeDecoration = refs/gitbutler`** in the local git config ([base.rs#L302-L310](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-branch-actions/src/base.rs#L302-L310)).
- **Cross-process locking is still best-effort.** The hard guarantee is "in-process exclusivity only" ([but-ctx/access.rs#L21-L36](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-ctx/src/access.rs#L21-L36)). Two agents running `but` at once rely on that file lock.

### How the workspace commit is built and rebuilt

- **Tree:** a merge of every applied stack tip. Parents: the tips themselves (or the target commit if none) ([commit/mod.rs#L678-L736](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/commit/mod.rs#L678-L736)). Author is "GitButler". The message lists each branch and its head and says "If you commit on this branch, GitButler will throw it away."
- **Merge order matters.** Tips are merged one by one, each time with the lowest merge-base so far ("This is critical: we enforce using the lowest merge-base", [commit/mod.rs#L350-L366](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/commit/mod.rs#L350-L366)). The legacy path does the same fold from an octopus merge-base ([legacy/head.rs#L44-L107](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/legacy/head.rs#L44-L107)).
- **A stack that conflicts is left out, not merged with conflicts.** Merges are "fail fast". A conflicting tip is skipped ("Ignore this stack, continue with the others"), and a "hero" stack being applied wins over others ([commit/mod.rs#L325-L393](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/commit/mod.rs#L325-L393), [#L540-L542](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/commit/mod.rs#L540-L542)). The legacy builder treats such a conflict as a bug: "This branch should have already been unapplied" ([legacy/head.rs#L94-L100](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/legacy/head.rs#L94-L100)).
- **Rebuilt after every mutation.** In the graph editor the workspace commit is just another pick with `conflictable: false`, so a rewrite that would make it conflict fails instead of storing a conflicted workspace commit ([graph_rebase/mod.rs#L104-L116](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-rebase/src/graph_rebase/mod.rs#L104-L116), [#L63-L66](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-rebase/src/graph_rebase/mod.rs#L63-L66)). The legacy `update_workspace_commit` re-merges from metadata, rewrites the commit, force-moves the ref and sets HEAD ([integration.rs#L61-L217](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-branch-actions/src/integration.rs#L61-L217)).
- **One branch needs no workspace commit.** Unapply's default disposition drops the workspace ref when one named tip is left and checks out that branch directly ([unapply.rs#L80-L100](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/branch/unapply.rs#L80-L100), [#L438-L463](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/branch/unapply.rs#L438-L463)). Applying a second branch from a normal branch re-creates the workspace commit with both ([apply.rs#L371-L408](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/branch/apply.rs#L371-L408)).

### The index and the working directory

- **The index is kept equal to the workspace commit's tree.** The legacy path does `index.read_tree(workspace_tree)` ([integration.rs#L204-L206](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-branch-actions/src/integration.rs#L204-L206)). The docs: "we modify your index to look like the union of all the committed states of all your applied parallel branches" ([workspace-branch.mdx#L45-L49](https://github.com/gitbutlerapp/gitbutler-docs/blob/fde5f9265e7f8aa37377919c851cc744a97f1e8a/content/docs/workspace-branch.mdx#L45-L49)). So anything a human stages with `git add` is overwritten at the next rebuild **(inferred)**. GitButler's per-lane "staging area" is its own hunk-assignment table, not git's index.
- **Every checkout is a 3-way merge that keeps WIP.** `safe_checkout_from_head` merges (old HEAD tree, working directory, new tree): "We will always handle changes in the worktree safely to avoid loss of uncommitted information" ([checkout/function.rs#L15-L24](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/worktree/checkout/function.rs#L15-L24), [#L80-L171](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/worktree/checkout/function.rs#L80-L171)).
  - By default a conflict aborts: "Uncommitted files would be overwritten by checkout".
  - Graph-editor operations in the main worktree allow the conflict and write conflict stages into the index ([materialize.rs#L248-L281](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-rebase/src/graph_rebase/materialize.rs#L248-L281): "Allow for our worktree."). The desktop app warns that "conflict markers will be added to your uncommitted work" ([IntegrateUpstreamModal.svelte#L283-L291](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/apps/desktop/src/components/upstream/IntegrateUpstreamModal.svelte#L283-L291)).

  2. If stacks can't be read, it walks first parents from the workspace ref back to the last "GitButler Workspace Commit" and moves the ref there, "Undoing these commits but keeping the changes in your working directory" ([#L333-L445](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/command/legacy/teardown.rs#L333-L445)).

## 2. Dependent and adjacent hunks **[13]**

### How a hunk gets "locked" to another branch

- **Definition.** "a patch being 'dependent' on another patch if it cannot be applied on top of another one, without leading to a merge conflict of the stacks. The stacks ... need to be independently mergeable to main and with each other" ([but-hunk-dependency/README.md#L7-L9](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/README.md#L7-L9)).
- **Algorithm.** A blame-like list of line ranges per file. Each range is tagged with a stack and a commit. Each stack's commits are replayed from base to tip. The stacks are then combined into workspace line numbers, "assumed and required to be independent without overlap" ([ranges/mod.rs#L82-L90](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/src/ranges/mod.rs#L82-L90)).
- **0 context lines** for both commit hunks and worktree hunks ([lib.rs#L193](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/src/lib.rs#L193), [ui.rs#L57](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/src/ui.rs#L57)).
- **The overlap test is strict**: `self.start <= incoming_last_line && last_line >= start` on inclusive ranges, so touching ranges do not count ([ranges/hunk.rs#L145-L179](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/src/ranges/hunk.rs#L145-L179)).
- **A 1-line margin applies in only two cases** ([ranges/mod.rs#L143-L180](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/src/ranges/mod.rs#L143-L180), [hunk.rs#L181-L186](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/src/ranges/hunk.rs#L181-L186)):
  - a pure insertion next to a commit's deletion point;
  - a hunk whose content looks like a reorder or move.
  - "Plain substitutions (where none of the old lines appear in the new lines) are not flagged."
  - The margin was added on 2026-03-19 because "the existing strict-overlap check misses the dependency. Cherry-picking that commit then fails" ([c8a10f7e](https://github.com/gitbutlerapp/gitbutler/commit/c8a10f7ef6bd27de8e576cb50ca96212a7b3b821)).
- **A file another branch added or deleted locks the whole file**: "For additions and deletions, we consider the hunk to always intersect" ([ranges/mod.rs#L175-L178](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/src/ranges/mod.rs#L175-L178)). So if session A's branch created a file, every edit B makes to it locks to A **(inferred)**.
- **Result shape.** Each hunk gets a list of `HunkLock { target: Stack(id) | Unidentified, commit_id }`. A hunk "can be locked to more than one branch if it overlaps with more than one committed hunk" ([ui.rs#L82-L99](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-dependency/src/ui.rs#L82-L99)).

### Locks no longer decide where a hunk goes

- **Before March 2026** a hunk locked to one stack was forced onto it. A hunk locked to two stacks became unassigned: "the user can resolve this by partial committing" ([lib.rs at 43b160e4, #L597-L610](https://github.com/gitbutlerapp/gitbutler/blob/43b160e46183aeebbcac107718947dcddbc6f216/crates/but-hunk-assignment/src/lib.rs#L597-L610)).
- **Since 2026-03-18** ([9ac5661b](https://github.com/gitbutlerapp/gitbutler/commit/9ac5661b86ab917ee2ffcf3f53545a2a338aeccf), "assignments compute: disregard locks") locks and assignments are computed separately and both sent to the UI ([handler.rs#L142-L169](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-watcher/src/handler.rs#L142-L169)). Any hunk may be assigned to any branch ([hunk-assignment/lib.rs#L604-L652](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-assignment/src/lib.rs#L604-L652)).
- **When two hunks merge** "(due to edits causing the contexts to overlap), the id of the hunk with the most lines is adopted" ([hunk-assignment/lib.rs#L30-L36](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-assignment/src/lib.rs#L30-L36), [reconcile.rs#L85-L92](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-hunk-assignment/src/reconcile.rs#L85-L92)). So when two lanes' edits grow into one hunk (3 context lines by default), the whole hunk silently moves to the bigger one's lane **(inferred)**.
- **The CLI no longer assigns at all**: "nothing under crates/but/src creates an assignment" ([71938032](https://github.com/gitbutlerapp/gitbutler/commit/7193803291356e7254fc5080f3f4cd67888cf285), 2026-07-26; [6bdb2378](https://github.com/gitbutlerapp/gitbutler/commit/6bdb23782c5894641efccc205df135631307d446) "Eliminate hunk-assignments from the CLI"). Agents pick hunks by ID at commit time (section 5).

### What happens when you commit a hunk next to another branch's lines

- **Commit = cherry-pick from the workspace tree.** The selected changes are applied to `HEAD^{tree}`. That tree is then 3-way merged onto the target branch (base = workspace tree, ours = branch tree, theirs = changed tree). Any conflict rejects that file with `CherryPickMergeConflict`, and the commit is retried without it ([but-core/tree/mod.rs#L118-L156](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/tree/mod.rs#L118-L156), reasons at [#L10-L30](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/tree/mod.rs#L10-L30)).
- **The merge treats touching changes as a conflict.** gitoxide (pinned by GitButler): "Like Git, consider changes disjoint only if there is a gap between their base ranges" ([gix-merge utils.rs#L422-L425](https://github.com/GitoxideLabs/gitoxide/blob/79f388066484c445c038823b2201220e34b0b312/gix-merge/src/blob/builtin_driver/text/utils.rs#L422-L425)). This matches what we verified with git.
- **So the two checks disagree on adjacency** **(inferred from the two code paths above)**:
  - A substitution on the line right next to another branch's change is not shown as locked.
  - Committing it to its own branch is still rejected, for the whole file.
  - The CLI admits the gap: "adjacent insertions, for example, do not intersect as ranges", so it reports "suspected branches" instead ([but/utils/rejection.rs#L140-L146](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/utils/rejection.rs#L140-L146)).
- **No Mixed commit.** Because the base side holds the other branches' lines and the result is merged onto the target branch, another branch's lines never land in the commit; the file is rejected instead **(inferred)**.
- **CLI vs desktop.** The CLI rolls back the whole commit on any rejection and hints `but move X --above Y` ([commit.rs#L427-L429](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/command/legacy/commit.rs#L427-L429), [rejection.rs#L276-L282](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/utils/rejection.rs#L276-L282)). The desktop app commits the accepted files and returns the rejected ones ([commit_create.rs#L77-L104](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/commit/commit_create.rs#L77-L104)).
- **The docs still promise the opposite**: "you can be sure that all branches that you create from it will merge cleanly" ([virtual-branches.mdx#L30](https://github.com/gitbutlerapp/gitbutler-docs/blob/fde5f9265e7f8aa37377919c851cc744a97f1e8a/content/docs/features/branch-management/virtual-branches.mdx#L30)).

### When branches get stacked

- **Only by explicit action**: `create_reference` with an anchor, or `but move <branch> --above <branch>` ([create_reference.rs#L3-L10](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/branch/create_reference.rs#L3-L10), [stacked-branches.mdx#L34-L39](https://github.com/gitbutlerapp/gitbutler-docs/blob/fde5f9265e7f8aa37377919c851cc744a97f1e8a/content/docs/features/branch-management/stacked-branches.mdx#L34-L39)). No code stacks on a lock. The CLI only hints, and only "when there is exactly one dependency branch" ([rejection.rs#L276-L282](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/utils/rejection.rs#L276-L282)).
- **For agents the docs make it a prompt**: "If one session starts depending on another, make that relationship explicit by stacking the branches" and "If two sessions touch the same file or generated output, have the agents call out the overlap before committing" ([parallel-agents.mdx#L23-L24, #L61-L70](https://github.com/gitbutlerapp/gitbutler-docs/blob/fde5f9265e7f8aa37377919c851cc744a97f1e8a/content/docs/ai-agents/parallel-agents.mdx#L61-L70)).
- **Two parallel branches that conflict cannot both be applied.** The workspace merge skips the conflicting one (section 1). Applying a branch defaults to `AbortAndReportConflictingStacks`, which saves nothing ([branch/mod.rs#L466-L476](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/branch/mod.rs#L466-L476), [but-api/branch.rs#L869-L871](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-api/src/branch.rs#L869-L871)).

## 3. Upstream **[12] [14]**

- **`but pull`** "fetches the latest changes from the remote and rebases all applied branches and linked worktrees on top of the updated target branch" ([args/mod.rs#L468-L481](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/args/mod.rs#L468-L481)). It builds one "rebase" update per lane bottom ([but-api/workspace.rs#L679-L697](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-api/src/workspace.rs#L679-L697)).
- **Merging is possible but not exposed.** The core also offers "Create a merge commit at the top of the selected stack", only for single-branch stacks ([upstream_integration.rs#L26-L34](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/upstream_integration.rs#L26-L34)). Neither the CLI nor the desktop app sends it **(inferred from callers)**.
- **Commits already upstream are dropped**: "dropping commits that are included content-wise upstream" ([upstream_integration.rs#L107-L112](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/upstream_integration.rs#L107-L112)).
- **A commit counts as integrated** if it is reachable from the target, matches an upstream commit by content, or is covered by a merged PR ([upstream_integration.rs#L65-L95](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/upstream_integration.rs#L65-L95)). Content matching hashes either commit data or the commit's diff, and also detects squash merges of a whole branch ([changeset.rs#L113-L154](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/changeset.rs#L113-L154), [upstream_integration.rs#L792-L809](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/upstream_integration.rs#L792-L809)).
- **An integrated branch is deleted locally**, not archived: "Remove integrated refs from the workspace and from git", except local `main`, `master` and the target ([upstream_integration.rs#L407-L444](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/upstream_integration.rs#L407-L444), [#L998-L1021](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-workspace/src/upstream_integration.rs#L998-L1021)). The CLI prints "has been integrated upstream and removed locally" ([pull/mod.rs#L536-L547](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/command/legacy/pull/mod.rs#L536-L547)).
- **Conflicts never stop the rebase.** A conflicting commit is stored as a "conflicted commit" ([commit/conflict.rs#L3-L24](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/commit/conflict.rs#L3-L24)):
  - Its subject gets a `[conflict] ` prefix and a `GitButler-Conflict:` trailer.
  - Its tree is the "ours" auto-resolution plus `.conflict-side-0`, `.conflict-side-1`, `.conflict-base-0`, `.auto-resolution` and `.conflict-files` directories.
  - Plain git sees those directories as real files in the commit. GitButler refuses to check such a commit out ([checkout/function.rs#L41-L51](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-core/src/worktree/checkout/function.rs#L41-L51)).
- **Uncommitted work is not stashed.** It is 3-way merged onto the new workspace tree, and conflicts become conflict markers in the files (section 1, index and working directory). The update is wrapped in a `MergeUpstream` snapshot saved only on success ([but-api/workspace.rs#L828-L883](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-api/src/workspace.rs#L828-L883)).

What this means for "throw away one session" **(inferred from the table)**:

- In GitButler, `but branch delete` removes a branch's commits.
- Its uncommitted changes have no owner in the CLI, so someone must pick them by hunk ID and `but discard` them.
- Re-applying an unapplied branch does not turn "WIP Assignments" back into uncommitted changes. A grep finds only the code that creates it.

### The oplog

- **What a snapshot holds** ([oplog.rs#L116-L144](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-oplog/src/oplog.rs#L116-L144)): a git tree with
  - the index and its conflicts;
  - the target tree;
  - `virtual_branches.toml`, `project_meta.toml`, `branch_order.toml`;
  - for each applied branch, its commits and tree;
  - the checkout ref and commit;
  - `worktree/`: tracked and untracked, non-ignored files.
- **No size limit.** `AUTO_TRACK_LIMIT_BYTES = 0`, "**Inactive for now** while it's hard to tell if it's safe *not* to pick up everything" ([oplog.rs#L37-L39](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-oplog/src/oplog.rs#L37-L39)). I found no pruning **(unverified)**.
- **Where it is stored.** Snapshots are a chain of commits whose head is in `.git/gitbutler/operations-log.toml` ([gitbutler-oplog/lib.rs#L12](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-oplog/src/lib.rs#L12)). They are kept from gc by a fake reflog entry on `refs/heads/gitbutler/target`, so that "The oplog must not be visible in `git log --all` as branch" ([reflog.rs#L37-L56](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-oplog/src/reflog.rs#L37-L56)).
- **Restore is repository-wide.** It first snapshots the current state, recreates missing commits, then checks out the snapshot's full working-directory tree "as-is", replacing all current uncommitted changes ([oplog.rs#L1086-L1137](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-oplog/src/oplog.rs#L1086-L1137), [#L1294-L1311](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-oplog/src/oplog.rs#L1294-L1311)). So undoing session A's delete also rewinds session B's WIP to that moment **(inferred)**.
- **`but undo`** restores the most recent snapshot, whichever session caused it ([undo_redo.rs#L155-L202](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/command/legacy/undo_redo.rs#L155-L202)). `but oplog restore <sha>` picks one: "All state is preserved in operations, including uncommitted changes" ([args/oplog.rs#L9-L20](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but/src/args/oplog.rs#L9-L20)).
- **Gaps:**
  - Branches that were already unapplied at snapshot time are not stored or recreated ([oplog.rs#L920-L926](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-oplog/src/oplog.rs#L920-L926), [#L1345-L1352](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-oplog/src/oplog.rs#L1345-L1352)).

  - The newer `but-oplog` design note says uncommitted files should *not* be tracked ("Note the absence of uncommitted and untracked files"), though the current backbone stores them ([but-oplog/lib.rs#L13](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-oplog/src/lib.rs#L13), [#L48-L49](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/but-oplog/src/lib.rs#L48-L49)).

## 6. License **[why]**

A reading of the license text, not legal advice.

- **What it covers.** "The 'Software' is each version of the software that we make available" ([LICENSE.md#L17-L21](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/LICENSE.md#L17-L21)). The grant is to "use, copy, modify, create derivative works ... and redistribute the Software for any Permitted Purpose" ([#L23-L28](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/LICENSE.md#L23-L28)).
- **What it bars.** A "Competing Use": "making the Software available to others in a commercial product or service that ... offers the same or substantially similar functionality". Internal use, "non-commercial education" and "non-commercial research" are named as permitted ([#L30-L52](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/LICENSE.md#L30-L52)). Reading the code to learn its design is research.
- **Copied code carries the terms.** "The Terms and Conditions apply to all copies, modifications and derivatives of the Software" ([#L62-L69](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/LICENSE.md#L62-L69)). Code copied or translated from GitButler could not ship under MIT or Apache-2.0, because anyone downstream could then use it commercially.
- **Ideas are not covered.** The text grants and limits rights in "the Software" only. It says nothing about designs, algorithms or behaviour. Code we write ourselves from a design is outside it, as long as it is not a copy or derivative.
- **Patents.** The patent licence covers only Permitted Purposes ([#L54-L60](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/LICENSE.md#L54-L60)). A web search found no GitButler patents **(unverified: no USPTO or Google Patents search done)**.
- **Names.** No right to use "our trademarks, trade names, service marks or product names" ([#L81-L85](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/LICENSE.md#L81-L85)).
- **Each version turns MIT after two years** ([#L87-L92](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/LICENSE.md#L87-L92)). The FSL FAQ: "The two year timeframe applies to each software version that is made available. Methods of making software available include pushing a Git commit" ([fsl.software](https://fsl.software/)). So every GitButler commit pushed before about 2024-10-15 is usable under MIT today. That predates the current graph editor, `but-hunk-dependency` and the oplog's current form **(inferred from file history)**.
- **Not OSI.** FSL calls itself "Fair Source" that becomes Open Source after two years ([fsl.software](https://fsl.software/)).

## Implications (facts and constraints, no decisions)

### For ticket 12, "What the workspace looks like to plain git"

1. GitButler's answer to "what does plain git see" is a merge commit on a dedicated branch name, an index forced to that merge's tree, and two git hooks. It is retreating from that: single-branch mode is now default, the hooks are "legacy", and the workspace commit appears only when a second branch is applied.
2. With one applied branch, HEAD can sit on the real branch and plain git works normally. The merge commit only pays for itself with two or more branches.
3. The weak spot is a plain `git commit` that bypasses the hook. GitButler then refuses to work until `but teardown` or `git reset --soft`. It does not adopt the stray commit into a branch.
4. Plain `git stash`, `git reset --hard` and `git checkout -- .` act on everyone's WIP and are not guarded. GitButler's only defence is an oplog snapshot taken by some earlier `but` command.
5. Session branches as plain `refs/heads/*` names work for GitButler. Its metadata lives outside refs, in `.git/gitbutler/`.
6. Conflicted commits are stored *in* history with extra directories in the tree. Plain git sees them as ordinary files.

### For ticket 13, "Changes that can't stand on their own session branch"

7. GitButler has two adjacency rules that disagree. The lock check has no margin for substitutions; the commit check has git's margin. Our design can avoid this by using one rule for both, the merge rule.
8. GitButler's way out is rejection plus a stacking hint, never a Mixed commit and never automatic stacking. It used to force a locked hunk onto its branch (a Mixed commit for the session that wrote it), and dropped that in March 2026.
9. A file created on one branch locks every later edit to it from any branch.
10. When two hunks merge because their context overlaps, GitButler gives the whole hunk to the larger one's branch, silently. With 3 context lines, edits up to about 6 lines apart can end up in one hunk **(inferred from how unified diffs join hunks)**.
11. Two branches that conflict cannot both stay applied, because the workspace merge drops the conflicting one. So "let the branches conflict and resolve at merge time" also means "one of them leaves the shared working directory".

### For ticket 14, "Throwing away all of one session's work"

12. In GitButler, deleting a branch's commits and discarding its WIP are separate commands. The WIP side needs an owner GitButler no longer tracks in the CLI.
13. Undo is a whole-repo time machine. It brings back deleted commits and WIP, but it also rewinds every other session's WIP to that moment, and `but undo` takes whatever operation ran last.
14. Unapply is a reversible "put away" with a known gap: re-applying does not restore the WIP as uncommitted changes. Branches unapplied before a snapshot cannot be brought back from it.
15. An integrated or upstream-merged branch is deleted locally by `but pull`. A pushed branch is never deleted on the remote by any of these commands **(inferred: no remote deletion found in these paths)**.

### For "why not GitButler?"

16. GitButler now leaves "which changes are mine" to each agent's judgement, through instructions in `CLAUDE.md` and a skill. It records no ownership, and nothing covers Bash or hand edits.
17. It requires agents to learn `but` and to avoid git writes. Our pitch is the opposite: plain git, no new CLI for agents.
18. Its license is FSL-1.1-MIT, not OSI. Its design can be studied freely; its recent code cannot be reused in an MIT project until two years after each commit.
19. Its undo is repository-wide, not per session.
