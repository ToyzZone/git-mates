# Detecting changes that bypass Claude Code's Edit and Write hooks

Date: 2026-10-15
Ticket: [03 Detecting changes that bypass Claude Code hooks](../.scratch/agent-ready-vcs/issues/03-detecting-changes-outside-hooks.md)
Method: primary sources only. I read the source code of GitButler, jj, re_gent, Entire CLI, the Rust `notify` crate and git's fsmonitor daemon at pinned commits, plus the Linux man pages and kernel source, Apple's FSEvents and Endpoint Security headers from the macOS 27 SDK, the Watchman docs and the Claude Code docs. Every claim links to its source. Anything I could not confirm is marked **(unverified)**.

Related: [claude-code-hooks-for-ownership.md](claude-code-hooks-for-ownership.md) covers hook payloads in detail; this file covers how to see changes that no Edit or Write hook reports.

## Summary

- **No mechanism tells you which process wrote a file, unless it has privileges.** inotify "provides no information about the user or process that triggered the inotify event". FSEvents can only mark events caused by the watching process itself. Only Linux fanotify (with `CAP_SYS_ADMIN`) and macOS Endpoint Security (with an entitlement you must request from Apple) report the writing process. So with all three approaches in the ticket, **concurrent Bash calls in two sessions cannot be told apart**. Each approach only knows *when* a path changed, not *who* changed it.
- **Snapshot diff around each Bash call** is exact for one call running alone. Its cost is two working-tree status walks per call, which git's own fsmonitor and untracked cache make cheap. It misses commands that keep running after PostToolUse (`run_in_background`, and foreground commands that hit their timeout and move to the background). It blames everything that changed in the window on the session whose call was running.
- **Continuous watching** (`notify` over FSEvents or inotify) sees every change, including the human's, with timestamps. It needs a long-running process, because hooks are one-shot. It can drop events (queue overflow, a new subdirectory before its watch is added, FSEvents "must scan subdirs"), so it always needs a rescan path. On Linux it costs one inotify watch per directory, ignored directories included unless you plan around them. `notify` does no `.gitignore` filtering.
- **git fsmonitor or Watchman** is the same OS mechanism behind a daemon. It answers "which paths may have changed since token T", and a "cookie" file makes each answer include every change made before the query. It speeds up a snapshot diff. It does not solve ownership. Neither the daemon nor Watchman reads `.gitignore`: git applies ignore rules on the client side, and Watchman only has `ignore_dirs`. git's built-in daemon gained Linux support in **git 2.55.0**.
- **Claude Code now does a snapshot diff itself.** Since v2.1.269, PostToolUse for Bash can receive `tool_response.bashEditDiff`: the files that changed under the repository while the command ran, git-ignored files excluded. It has a `shared` flag for a concurrent Bash call. It is beta, off by default outside auto and bypass modes, capped at 200 paths, and documented as "best effort".
- **The four tools:** GitButler watches with `notify` and runs a full status on each event. Its Claude Code hooks (removed 2026-05-19) only claimed `Edit|MultiEdit|Write` hunks and left Bash changes unassigned. jj walks the whole tree on every command and can use Watchman to narrow the walk. It has no notion of who changed anything. re_gent re-reads and hashes the whole tree at every Stop and credits every difference to the stopping session. Entire runs `git status` at turn start and turn end. Its own code comments admit the race: "the first to stop would claim both".

## Platform facts

### inotify (Linux)

From [inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html), man-pages 6.19:

- **Not recursive.** "Inotify monitoring of directories is not recursive: to monitor subdirectories under a directory, additional watches must be created. This can take a significant amount time for large directory trees."
- **New-directory race.** By the time you watch a new subdirectory, "new files (and subdirectories) may already exist inside the subdirectory", so you must scan it right after adding the watch.
- **Overflow.** "The event queue can overflow. In this case, events are lost." Excess events "are dropped, but an IN_Q_OVERFLOW event is always generated."
- **No writer.** "The inotify API provides no information about the user or process that triggered the inotify event."
- **Blind spots.** `mmap` writes are not reported. Network filesystems produce no events for remote changes. Pseudo-filesystems are not monitorable.
- **Renames.** Matching `IN_MOVED_FROM` with `IN_MOVED_TO` "is thus inherently racy".
- **Defaults** (kernel source, [inotify_user.c](https://github.com/torvalds/linux/blob/0fcb05b72344f40806cbe810de8872f1698bf053/fs/notify/inotify/inotify_user.c#L805-L843)):
  - `max_user_watches`: 1% of low memory divided by the per-watch cost, clamped to [8192, 1048576].
  - `max_queued_events`: 16384.
  - `max_user_instances`: 128.
  - git's own docs still say "typically 8192" ([git-fsmonitor--daemon](https://git-scm.com/docs/git-fsmonitor--daemon)). That is the floor of the clamp.

### FSEvents (macOS)

From the macOS 27 SDK header `FSEvents.framework/Headers/FSEvents.h` (Apple's header doc comments):

- **File-level events are opt-in.** `kFSEventStreamCreateFlagFileEvents` (10.7+) gives "file-level notifications ... instead of only receiving directory level notifications. Use this flag with care as it will generate significantly more events". Apple's 2012 programming guide still describes only directory-level granularity: "It tells you *only* that something in the directory has changed" ([Technology Overview](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/TechnologyOverview/TechnologyOverview.html)).
- **Dropped events.** `kFSEventStreamEventFlagMustScanSubDirs` means "Your application must rescan not just the directory given in the event, but all its children, recursively". It comes with `UserDropped` or `KernelDropped` when buffering failed.
- **Not a log.** "Event flags are simply hints ... the FSEvent stream should NOT be treated as a form of historical log that could somehow be replayed to arrive at the current state of the file system ... what is actually in the file system can change immediately after you check it."
- **Only your own process is identifiable.** `kFSEventStreamCreateFlagMarkSelf` (10.9+) tags "events that were triggered by the current process" with `OwnEvent`, and `IgnoreSelf` drops them. Extended data carries `path`, `fileID` (inode) and `docID`, with no process ID.
- **History.** Events can be replayed from an event ID (`sinceWhen`). `kFSEventStreamCreateFlagFullHistory` (10.15+) avoids skipping events "near the time of an unclean restart of the client process". The persistent database lets you "see changes that occurred even while your application was not running" ([Technology Overview](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/TechnologyOverview/TechnologyOverview.html)).
- **Latency.** Without `NoDefer`, events within a latency window are delivered as one group. With it, the first event after a quiet period is delivered at once.

### Only privileged APIs name the writing process

- **Linux fanotify.** Event metadata has a `pid` field: the process that caused the event ([fanotify(7)](https://man7.org/linux/man-pages/man7/fanotify.7.html)). Watching a whole mount "offers the capability to monitor a whole directory tree in a race-free manner." Before Linux 5.13 it required `CAP_SYS_ADMIN`. Since then, unprivileged users can use it with limits: they may only mark inodes, and "A user will also not receive the pid that generated the event, unless the listening process itself generated the event" ([fanotify_init(2)](https://man7.org/linux/man-pages/man2/fanotify_init.2.html)). Create, delete and move events need a group that reports file handles (`FAN_REPORT_FID`, Linux 5.1+).
- **macOS Endpoint Security.** It has `ES_EVENT_TYPE_NOTIFY_WRITE`, `CREATE`, `RENAME`, `UNLINK` and `CLOSE`, each with the acting process (SDK `EndpointSecurity/ESTypes.h`, `ESMessage.h`).
  - The entitlement: "You must request this entitlement from Apple" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.endpoint-security.client)).
  - `es_new_client` also fails with `ERR_NOT_PRIVILEGED` ("not running as root") or `ERR_NOT_PERMITTED` (no TCC approval, that is, Full Disk Access).
  - The macOS 27 SDK adds `es_new_descendants_client`. It receives events only for "the entire subtree rooted at the calling process". It still "Requires the com.apple.developer.endpoint-security.client entitlement", but "Does NOT require root privilege" and "Does NOT require TCC approval" (`ESClient.h`).
  - Watchman's docs report that Apple's suggested fix for FSEvents ordering is "a watcher with Endpoint Security. Nobody has evaluated the feasibility of this yet" ([cookies](https://facebook.github.io/watchman/docs/cookies)).

### The `notify` crate (Rust)

Read at [a0864543](https://github.com/notify-rs/notify/tree/a0864543afb5414d12d21da4cbfd50c28b69ec71), which is 9.0.0-rc.5. The latest stable release on crates.io is 8.2.0 (2025-08-03), and GitButler pins it.

- **Backends:** FSEvents (macOS default, kqueue optional), inotify (Linux, and FreeBSD 14.5+), ReadDirectoryChangesW (Windows) and a `PollWatcher` fallback ([lib.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/lib.rs#L13-L25)). Its macOS stream uses `FileEvents | NoDefer | WatchRoot` with latency 0 by default ([fsevent.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/fsevent.rs#L392-L399), [config.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/config.rs#L214-L250)). It starts "since now", so FSEvents history replay is not used ([fsevent.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/fsevent.rs#L395)).
- **Its own "Known Problems"** ([lib.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/lib.rs#L35-L107)):
  - Network filesystems may emit no events.
  - Editors save files in different ways.
  - Inotify limits: "for recursive watched folders each file and folder inside counts towards the limit".
  - On large trees, "notify may fail to receive all events ... the linux backend is documented to not be a 100% reliable source".
  - APFS `std::fs::copy` can fire events on the *source* file.
- **Recursion on Linux** is emulated by walking the tree and adding a watch per directory ([inotify.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/inotify.rs#L610-L660)). There is no ignore-pattern filter.
- **Lost events become a `Rescan` flag.** inotify `Q_OVERFLOW` and FSEvents `MustScanSubDirs` both arrive as `Flag::Rescan`: "events received so far can no longer be relied on to represent the state of the filesystem now" ([event.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify-types/src/event.rs#L680-L700), [inotify.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/inotify.rs#L339-L340)).
- **`process_id` is "experimental"** ([event.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify-types/src/event.rs#L544-L552)). It is set only from FSEvents' `OwnEvent`, that is, the watcher's own process ([fsevent.rs](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/fsevent.rs#L211-L225)). notify does not set `MarkSelf` when it creates the stream, so in practice it is never set **(inferred from the flags at [fsevent.rs#L397-L399](https://github.com/notify-rs/notify/blob/a0864543afb5414d12d21da4cbfd50c28b69ec71/notify/src/fsevent.rs#L397-L399); not tested)**.

### git fsmonitor

- **Two forms.** `core.fsmonitor=true` runs the built-in daemon. A path runs a hook such as Watchman's ([core.adoc](https://github.com/git/git/blob/6de20f6092dcf9bdb1c8efe03db4b70c82b423dd/Documentation/config/core.adoc#L64-L99)).
- **Hook contract:** "output ... the list of all files in the working directory that may have changed since the requested time. The logic should be inclusive ... It is OK to include files which have not actually changed." Version 2 uses an opaque token ([githooks](https://github.com/git/git/blob/6de20f6092dcf9bdb1c8efe03db4b70c82b423dd/Documentation/githooks.adoc#L714-L748)).
- **Platforms.** The daemon gained Linux support in 2.55.0 ("The fsmonitor daemon has been implemented for Linux", [RelNotes 2.55.0](https://github.com/git/git/blob/6de20f6092dcf9bdb1c8efe03db4b70c82b423dd/Documentation/RelNotes/2.55.0.adoc)). Backends are `fsm-listen-{darwin,linux,win32}.c`. The `core.fsmonitor` doc text still says "Windows and MacOS".
- **macOS backend:** FSEvents with `NoDefer | WatchRoot | FileEvents` ([fsm-listen-darwin.c](https://github.com/git/git/blob/6de20f6092dcf9bdb1c8efe03db4b70c82b423dd/compat/fsmonitor/fsm-listen-darwin.c#L416-L418)).
- **Linux backend:** inotify, with a watch added to every directory recursively ([fsm-listen-linux.c](https://github.com/git/git/blob/6de20f6092dcf9bdb1c8efe03db4b70c82b423dd/compat/fsmonitor/fsm-listen-linux.c#L265-L310)).
- **Cookies.** Before answering, the daemon creates a cookie file and waits up to 1 second for its own listener to see it ([fsmonitor--daemon.c](https://github.com/git/git/blob/6de20f6092dcf9bdb1c8efe03db4b70c82b423dd/builtin/fsmonitor--daemon.c#L186-L245)).
- **Tokens.** A new token ID is created at start, on any resync "such as when the kernel drops or we miss events", or on flush. A client with a stale token gets a "trivial response", meaning "anything may have changed" ([same file](https://github.com/git/git/blob/6de20f6092dcf9bdb1c8efe03db4b70c82b423dd/builtin/fsmonitor--daemon.c#L346-L367)).
- **Caveats** ([git-fsmonitor--daemon](https://git-scm.com/docs/git-fsmonitor--daemon)): it refuses network mounts by default and does not filter submodule events.
- **No public query command.** The daemon's subcommands are `start`, `run`, `stop` and `status`. Other programs benefit by running git commands, such as `git status` or `git diff`, with fsmonitor on.

### Watchman

- **`since` queries** return files "modified since a specific clockspec". After a restart, results are a fresh instance with `is_fresh_instance: true` ([file-query](https://facebook.github.io/watchman/docs/file-query)). jj treats that as "crawl the entire working copy" ([fsmonitor.rs](https://github.com/jj-vcs/jj/blob/9031d0a1669a262af10f95497a458f0084b28fbb/lib/src/fsmonitor.rs#L249-L262)).
- **Cookies** guarantee "Every file operation that happens before the query is started will be observed". On macOS, FSEvents "provides no guarantees here", and the docs suggest `settle_period` as a workaround ([cookies](https://facebook.github.io/watchman/docs/cookies)).
- **Ignore handling.** Only `ignore_dirs` and `ignore_vcs` (default `.git`, `.hg`, `.svn`). `settle` defaults to 20 ms ([config](https://facebook.github.io/watchman/docs/config)). A GitHub code search of `facebook/watchman` for "gitignore" returns no hits.
- **Triggers** run a command when files change. jj uses one to run `jj util snapshot` ([fsmonitor.rs](https://github.com/jj-vcs/jj/blob/9031d0a1669a262af10f95497a458f0084b28fbb/lib/src/fsmonitor.rs#L279-L304)).

### Claude Code's own signals

- **`bashEditDiff`** (v2.1.269+, public beta). It lists files that changed under a git repository while a Bash command ran. "Files that Git ignores and files in submodules aren't listed" ([hooks: Bash](https://code.claude.com/docs/en/hooks#bash)).
  - It is recorded in every mode only when `bashEditDiffEnabled` is `true` in user or managed settings. A repository's `.claude/settings.json` cannot turn it on ([settings](https://code.claude.com/docs/en/settings-reference#basheditdiffenabled)). Otherwise it is recorded only in auto and `bypassPermissions` modes, when Claude Code directs Claude to edit through Bash.
  - `changedFiles` holds at most 200 paths. `skipped` is set for `git checkout` and `git stash`. `shared` is set for a concurrent Bash call.
  - The docs warn: "Claude Code can miss a change, include a file that another process changed at the same time, or stop at its size limits ... Use the list to find what to review, not to enforce a policy."
- **`FileChanged`** uses "a filesystem watcher, not ... tool calls, so it runs the hook no matter what changed the file". But its matcher entries are "registered as a literal filename in the working directory", and more paths come only through `watchPaths`. It cannot block, and it has no writer field ([hooks: FileChanged](https://code.claude.com/docs/en/hooks#filechanged)).
- **Background commands.** `run_in_background` commands, and foreground commands moved to the background at their timeout, keep running after the tool call returns ([tools reference](https://code.claude.com/docs/en/tools-reference#background-commands)). "PostToolUse fires ... concurrently when Claude makes parallel tool calls" ([hooks: PostToolBatch](https://code.claude.com/docs/en/hooks#posttoolbatch)).

## How each tool detects working-directory changes

### GitButler

Read at [03dc9bd7](https://github.com/gitbutlerapp/gitbutler/tree/03dc9bd7a3944269042dcd2b8bb9e1288622e976).

- **Detection is a `notify` watcher plus a full status.**
  - The file monitor wraps `notify::RecommendedWatcher` in a vendored debouncer: a 100 ms tick (250 ms on Windows), a flush after 3 quiet ticks, and at most 60 s of buffering. A `flush()` handle forces the pending events out ([file_monitor.rs](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-filemonitor/src/file_monitor.rs#L25-L64)).
  - Every batch of worktree events triggers a full `but_core::diff::worktree_changes(&repo)` plus hunk assignment. The event paths are only passed on to the UI ([handler.rs](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-watcher/src/handler.rs#L130-L176)). So the watcher is a trigger, and the diff is the source of truth.
- **Two watch modes** ([file_monitor.rs](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-filemonitor/src/file_monitor.rs#L66-L83)):
  - **Legacy**, used everywhere except WSL: one recursive watch of the worktree.
  - **Modern**, the WSL default: an ignore-aware plan. Each non-ignored or tracked directory gets a non-recursive watch, and `.git` paths are watched first "so we still get critical git events even when we hit OS watch limits" ([watch_plan/mod.rs](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-filemonitor/src/watch_plan/mod.rs#L15-L105)).
  - When the limit is hit, it logs "continuing with partial watches. Monitoring coverage may be incomplete until restart".
  - Its own comment admits the new-directory race: "files created in a new directory before the watch is established will be missed".
- **`.gitignore`** is applied per event with gix excludes. A path stays reported if it is tracked in the index ([file_monitor.rs](https://github.com/gitbutlerapp/gitbutler/blob/03dc9bd7a3944269042dcd2b8bb9e1288622e976/crates/gitbutler-filemonitor/src/file_monitor.rs#L832-L876)).
- **Ownership from Claude Code hooks: removed.** Commit [1dbe2bdb](https://github.com/gitbutlerapp/gitbutler/commit/1dbe2bdbe88e6c79da228a8fa080985340a27f3a) (2026-05-19, "Remove agent/codegen integration") deleted the `but-claude` crate. Before that ([parent f9f34ce5](https://github.com/gitbutlerapp/gitbutler/tree/f9f34ce5c0d467adc23a26b42a2bf1faa7778f24/crates/but-claude/src/hooks)), it worked like this:

## Implications (facts and constraints, no decisions)

1. **No unprivileged mechanism, in any approach in the ticket, can name the session that changed a file.** Every option yields "path P changed between t1 and t2". When two sessions' Bash windows overlap, or the human types during a window, the evidence cannot split ownership. This holds for snapshot diff, `notify`, git fsmonitor, Watchman and Claude Code's `bashEditDiff` (`shared` flag).
2. **Process-level ownership needs privileges.** Linux needs fanotify with `CAP_SYS_ADMIN`; unprivileged fanotify withholds other processes' PIDs. macOS needs Endpoint Security with an entitlement Apple must grant. Plain `es_new_client` also needs root and Full Disk Access. macOS 27's `es_new_descendants_client` drops root and TCC, but only sees the caller's own process subtree. A hook process is not an ancestor of Claude Code's Bash commands, so that would require each Claude Code session to be launched under a process the layer controls **(inference)**.
3. **Overlap is the norm, not an edge case.**
   - Parallel tool calls in one session fire PostToolUse concurrently.
   - Subagents run in the background by default.
   - Background commands outlive their tool call, and a foreground command that hits its timeout moves to the background. So a window can stay open with no end hook.
   - Within one session, overlap does not affect ownership. Across sessions it does.
4. **The one race-free option found without privileges is to stop the windows from overlapping.** GitButler did this for Edit and Write: a per-file lock held from PreToolUse to PostToolUse. For Bash, a lock would have to be repo-wide, because the paths are not known in advance. It would cost parallelism. Background commands would still escape it.
5. **A snapshot diff only gives hunks if the before-state is kept.** `git status` compares against the index, not against the moment before the call. To give a Bash call's hunks to a session, the pre-call content of every path the call might touch must be saved. In practice that means every dirty or untracked file, plus the index state for clean files. re_gent stores whole trees for this. Claude Code's `bashEditDiff` returns diffs for at most 5 files and paths for at most 200.
6. **Cost is dominated by the untracked-file search, and git already has the fix.** `core.untrackedCache=true` plus `core.fsmonitor=true` makes repeated `git status` calls scale with recent changes, not tree size. That is now built in on macOS, Windows and Linux (git 2.55.0+). The first runs warm the caches.
   - Hand-rolled walks scale with tree size: re_gent reads every file, and Entire needed a 20 s cap.
   - The time a hook adds to each Bash call is open: see "Performance budget for hooks on large repos" in the [map](../.scratch/agent-ready-vcs/map.md).
7. **`.gitignore` comes free only through git.** The `notify`, git daemon and Watchman layers all report ignored paths. Some later step must filter them while keeping tracked files inside ignored directories, as GitButler does. On Linux the ignored directories also cost inotify watches, unless an ignore-aware watch plan skips them, as GitButler's Modern mode does. Then a `.gitignore` edit means re-planning.
8. **A watcher needs a daemon and a rescan path.** Hooks are one-shot processes. Every watcher can drop events: inotify overflow, the new-directory race, FSEvents `MustScanSubDirs`, or a daemon restart (stale token or `is_fresh_instance`). So "full rescan" must be a normal path, not an error path. A full rescan can tell *that* something changed, not *when*. That loses ownership for that interval.
9. **Human edits are only seen live by a watcher.** Without one, a human edit is noticed at the next snapshot, by any session's hook or a sweep. If it lands inside an agent's Bash window, it is credited to that agent. That contradicts the glossary rule that the **Human session** owns every change no agent session owns. A watcher with timestamps narrows this but does not close it, by implication 1.
10. **Claude Code's built-in Bash diff is an input, not a foundation.** It is beta, its shape "may change", it is off by default in default and plan modes, and a repo cannot turn it on. It skips `checkout` and `stash`, and it "can miss a change". It does use git's own ignore rules.
11. **Prior research needs one correction.** GitButler no longer has a Claude Code hooks integration (removed 2026-05-19). When it had one, it never claimed Bash-made changes.

## Not verified

- Whether `bashEditDiff`'s `shared` flag sees Bash calls in *other* Claude Code processes, or only calls in the same process (subagents). The docs' example is "a subagent's".
- How Claude Code computes `bashEditDiff`, for example by snapshotting through git. The docs only say git-ignored files and submodules are excluded.
- Whether `FileChanged`'s `watchPaths` accepts a directory and watches it recursively. The docs only describe files.
- That `notify`'s `process_id` is never set in practice (inferred from the stream flags, not tested). Also, which of the 9.0.0-rc.5 details used here also hold in 8.2.0, the version GitButler pins.
- Whether Entire sets go-git's `Worktree.Excludes`, which would pick up `core.excludesFile`. Also whether its pinned go-git pseudo-version (2026-09-17) matches the `main` code cited here.
- How hard it is to map a fanotify PID or an Endpoint Security process to a Claude Code session, given process ancestry and short-lived processes.
- The Watchman docs do not say outright that `.gitignore` is ignored. The claim rests on the config docs listing only `ignore_dirs` and `ignore_vcs`, a code search with no hits, and jj's TODO comment.
